# 원통 파우치 도안 — 설계 문서

작성일: 2026-08-23

## 1. 배경과 목적

지금 도구는 사각 파우치 한 종류만 만든다. 두 번째 형태로 **원통 파우치**를 더한다. 지퍼가 옆면을 앞쪽만 감싸고 뒤쪽은 안 끊겨, 그 부분이 경첩이 되어 뚜껑이 뒤로 젖혀지는 형태다. 원형 화장품 케이스나 반짇고리가 이 구조다.

계산 근거는 사용자가 준 도해다. 지름 130, 옆면 높이 130, 뚜껑 높이 30, 뒷면 길이 80인 예시와 그 전개도가 함께 있었다. 그 값들로 검산한다.

사각 파우치를 뜯어고치지 않는다. 사각은 "이어진 전개도 한 장", 원통은 "떨어진 조각 넷"이라 한 모양으로 묶으면 둘 다 이상해진다. **페이지를 만드는 기계만 공유하고, 무엇을 그릴지는 종류가 정한다.**

## 2. 범위

### 하는 것

- `/round/` 경로에 원통 파우치 전용 페이지를 만든다
- 지름·옆면 높이·뚜껑 높이 입력 → 조각 넷의 재단 도안
- 뒷면 비율을 선택 항목으로 조절 (기본 20%)
- 프리셋 3개
- A4/A3 1:1 실치수 타일링 PDF (기존 타일링 그대로)
- 두 페이지가 서로 오가는 링크
- 다운로드 기록에 `종류` 구분 추가
- Apps Script에 분당 상한

### 하지 않는 것 (의도적 제외)

- 사각 파우치 화면·계산 변경 (링크 한 줄 외)
- 한 페이지에서 종류를 고르는 UI — 페이지를 나누므로 필요 없다
- 가위집 표시 — 안내 문구로 대신한다
- 골선 반접기 — 원통 조각에는 접어서 반만 뽑을 대칭이 없다
- 겉감·안감·솜 구분, 손잡이 등 부속

## 3. 도안 계산 모델

### 3.1 입력과 상수

| 기호 | 의미 | 단위 |
|---|---|---|
| `D` | 뚜껑·바닥면 지름 (완성) | mm |
| `Hs` | 옆면 높이 (완성) | mm |
| `Hl` | 뚜껑 높이 (완성) | mm |
| `r` | 뒷면 비율 (기본 0.2) | — |
| `S` | 시접 = 10 (고정) | mm |
| `Z` | 지퍼 여유 = 10 (고정) | mm |

`S`와 `Z`는 사각 파우치와 같은 상수를 쓴다 (`core/constants.ts`). 지퍼 여유의 뜻도 같다 — 지퍼를 사이에 둔 두 조각이 합쳐 10mm를 내준다.

원주율은 `Math.PI`를 쓴다. 참고 도해는 3.14를 써서 `408.2`가 나오지만 우리는 `408.41`이 된다. 0.2mm 차이는 재봉에서 무의미하고, 상수를 따로 두면 "왜 3.14인가"를 설명할 자리가 계속 생긴다.

### 3.2 유도값

```
둘레      C  = D × π
뒷면 길이 Lb = C × r
앞면 길이 Lf = C − Lb
몸통 높이 Hb = Hs − Hl − Z
```

**핵심 제약: 앞면과 뒷면을 이어 붙인 둘레가 원둘레와 같아야 한다.** `Lf + Lb = C`가 정의상 항상 성립하므로 자동으로 지켜진다.

### 3.3 조각

완성 치수와 재단 치수(사방 시접 `S`).

| 조각 | 완성 | 재단 | 장수 |
|---|---|---|---|
| 뚜껑·바닥 원 | 지름 `D` | 지름 `D + 2S` | **2** |
| 앞면 윗단 | `Lf × Hl` | `(Lf + 2S) × (Hl + 2S)` | 1 |
| 앞면 아랫단 | `Lf × Hb` | `(Lf + 2S) × (Hb + 2S)` | 1 |
| 뒷면 | `Lb × Hs` | `(Lb + 2S) × (Hs + 2S)` | 1 |

네 조각 모두 모든 변이 다른 조각과 만나므로 **사방에 시접이 붙는다.**

원은 한 장만 그리고 라벨에 "2장"이라고 적는다. 지름 150 원 하나를 아끼면 종이가 크게 준다. 재봉 도안의 관행이기도 하다.

### 3.4 만드는 순서 (도안에 넣을 안내)

1. 앞면 윗단과 아랫단 사이에 지퍼를 단다 (지퍼 길이 `Lf` 이상)
2. 지퍼로 이어진 앞면의 좌우를 뒷면 좌우와 이어 원통을 만든다
3. 위 둘레에 뚜껑 원, 아래 둘레에 바닥 원을 붙인다
4. 곡선 시접에는 가위집을 넣는다

4번은 도안에 그리지 않고 화면 안내로만 둔다.

### 3.5 검산 (골든 케이스)

참고 도해의 `D=130, Hs=130, Hl=30, Lb=80`.

```
C  = 130 × π = 408.41      (도해는 3.14로 408.2)
r  = 80 / 408.41 = 0.1959  → 기본값 0.2와 사실상 같다
Lf = 408.41 − 81.68 = 326.73   (r=0.2일 때)
Hb = 130 − 30 − 10 = 90        (도해와 일치)
```

`Hb = 90`이 도해와 정확히 맞는다. `Lf`는 뒷면 비율을 0.2로 잡아 도해의 80 대신 81.68을 쓰므로 1.68mm 차이가 난다. 도해의 80을 그대로 쓰고 싶으면 선택 항목에서 비율을 조절한다.

### 3.6 유효 범위

| 값 | 범위 | 왜 |
|---|---|---|
| `D` | 80 ~ 300 | 80보다 작으면 원 시접(재단 지름 `D+20`)의 곡률이 심해 접히지 않는다 |
| `Hs` | 40 ~ 300 | 뚜껑 최소 10 + 지퍼 10 + 몸통 최소 20 = 40 |
| `Hl` | 10 ~ `min(Hs/2, Hs − Z − 20)` | 뚜껑이 몸통보다 길면 물건이 아니고, 몸통이 20보다 낮으면 물건이 안 들어간다 |
| `r` | 0.10 ~ 0.30 | 아래 참고 |

`Hl`의 상한이 두 겹인 이유가 있다. `Hs/2`만 걸면 `Hs=40, Hl=20`이 통과하는데 그때 몸통이 `40−20−10=10`밖에 안 된다. 반대로 `Hb ≥ 20`만 걸면 큰 파우치에서 뚜껑이 몸통보다 긴 조합이 통과한다. 둘 다 필요하다.

**뒷면 비율의 상한이 중요하다.** 지퍼가 원의 절반(180°)보다 짧으면 뚜껑이 물리적으로 젖혀지지 않는다. 0.3을 넘으면 열기 힘들고 0.5면 아예 안 열린다. 하한 0.1은 경첩이 흐물거리지 않게 하는 값이다.

**비율로 다루는 이유**가 여기 있다. `Lb`를 mm 고정값으로 받으면 지름을 바꿀 때 의미가 망가진다. 뒷면 80mm는 지름 130에서 19.6%지만, 지름 50에서는 50.9%가 되어 뚜껑이 안 열린다. 지름 300에서는 8.5%로 경첩이 너무 짧다.

`Hl`의 상한이 `Hs`에 딸려 있으므로 검증은 값 하나씩이 아니라 조합으로 해야 한다. 사각 파우치의 `validateDimensions`가 이미 조합 검사를 하므로 같은 모양을 따른다.

### 3.7 소수점 처리

둘레와 앞면 길이가 무리수가 된다. 사각 파우치와 같이 **계산은 실수로 하고 표시할 때만 소수 첫째 자리로 반올림**한다. 재단 치수를 미리 반올림하면 조각을 이어 붙일 때 오차가 쌓인다.

## 4. 조각 배치

### 4.1 규칙

폭이 넓은 조각부터 줄을 세우고, 남는 폭에 들어가는 조각을 같은 줄에 나란히 놓는다. 조각 사이 간격은 5mm — 가위가 지나갈 자리다.

빈틈없이 채우는 배치(bin packing)는 하지 않는다. 종이 몇 장을 아끼자고 조각이 매번 다른 자리에 가면 도안을 읽는 사람이 헷갈린다. **줄 순서가 늘 같은 편이 낫다.**

결과는 항상 세 줄이 된다:

```
1줄  [ 앞면 윗단 ]
2줄  [ 앞면 아랫단 ]
3줄  [ 원(2장) ] [ 뒷면 ]
```

### 4.2 종이 소모

| 입력 (D/Hs/Hl) | 전체 크기 | A4 | A3 |
|---|---|---|---|
| 80 / 60 / 20 | 221 × 200 | 2장 | 1장 |
| 130 / 130 / 30 | 347 × 320 | 4장 | 2장 |
| 160 / 100 / 25 | 422 × 320 | 6장 | 2장 |
| 200 / 160 / 40 | 523 × 420 | 6장 | 4장 |

기존 20장 경고가 그대로 적용된다.

### 4.3 출처 문구 자리

가장 큰 조각(앞면 아랫단) 한가운데에 넣는다. `titleScale(높이, 덩어리)`이 이미 "높이를 주면 배율을 준다"는 모양이라 그대로 부른다.

## 5. 구조

### 5.1 페이지를 나눈다

```
/          사각 파우치   (index.html · 지금 그대로)
/round/    원통 파우치   (round/index.html)
```

Vite의 여러 진입점으로 만든다. `base: './'`라 하위 경로에서 자산 경로가 `../assets/`로 알아서 맞는다. 실제로 만들어 확인했다 — 두 페이지 모두 오류 없이 뜨고 `src/core/`를 공유했다.

**페이지를 나누면 사이트 제목을 안 바꿔도 된다.** 각 페이지가 자기 제목을 가지므로 `사각사각 지퍼 파우치 패턴 나와라 얍!`이 그대로 살아 있고, 종류를 고르는 UI도 필요 없다. 각 화면이 지금처럼 단순하다.

두 페이지는 머리말 아래 한 줄로 서로를 가리킨다. 링크가 없으면 아무도 `/round/`를 못 찾는다.

### 5.2 모듈 경계

```
그대로 공유 — 손대지 않는다
  core/tiling.ts        totalWidthMm·totalHeightMm 두 개만 본다
  core/korean-font.ts   글자만 더한다
  core/constants.ts     SEAM_MM · ZIPPER_ALLOWANCE_MM
  track.ts · stale.ts   페이지 종류와 무관
  style.css             화면 규칙이 같다

pdf.ts에서 갈라낸다
  페이지 기계 (공유)    toFramePoint · toPagePoint · joinMarksFor ·
                        gridLabelPointMm · drawAlignmentMarks · drawJoinMarks ·
                        scaleSquareRectMm · drawScaleSquare · drawPatternNote ·
                        titleScale · 폰트 적재
  사각 전용 (남는다)    drawPolygon · drawSeamLine · drawFoldLine ·
                        drawFoldEdge · drawCenterAndTitle

원통이 새로 갖는 것
  core/round/layout.ts    조각 치수와 배치
  core/round/pdf.ts       조각 그리기
  ui/round/preview.ts     미리보기 SVG
  ui/round/shape.ts       완성 예상 사시도
  round/main.ts           화면 조립
```

`pdf.ts`를 파일 두 개로 쪼갤지 한 파일 안에서 나눌지는 구현할 때 정한다. 지금 700줄이 넘으므로 쪼개는 쪽이 유력하다.

### 5.3 데이터 흐름

사각과 같다. 입력 → 검증 → 조각 계산 → 타일링 → (미리보기 SVG | PDF).

타일링에 넘기는 것이 `Layout`이 아니라 `{ totalWidthMm, totalHeightMm }`만 있으면 되므로, 타일링의 시그니처를 그 모양으로 좁힌다. 사각 파우치의 `Layout`도 그대로 통과한다.

## 6. 화면

### 6.1 구성

사각 파우치 화면과 같은 뼈대를 쓴다. 입력 칸 셋, 완성 예상 그림, 프리셋, 용지 선택, 미리보기, 범례, 다운로드.

다른 점:

- 입력이 **지름·옆면 높이·뚜껑 높이**
- 선택 항목에 **뒷면 비율**이 는다 (`시접 추가`·`반접기`와 같은 자리)
- **반접기가 없다** — 원통 조각에는 접어서 반만 뽑을 대칭이 없다
- 범례에 골선·중앙선이 없다. `legendItems`가 이미 "실제로 그린 선만 담는다"는 규칙이라 자연스럽게 맞는다
- 곡선 시접 가위집 안내 한 줄

### 6.2 프리셋

| 이름 | 지름 / 옆면 / 뚜껑 |

| 동전·이어폰 파우치 | 80 / 60 / 20 |
| 화장솜 케이스 | 130 / 130 / 30 |
| 반짇고리 | 160 / 100 / 25 |

작은 것, 참고 도해와 같은 크기, 큰 것으로 잡았다. 반짇고리는 이 도구를 쓰는 사람이 재봉하는 사람이라 넣었다.

## 7. 한글 폰트

도안 이름과 조각 라벨에 새 글자가 든다. 본문용 서브셋에 **`글`·`동`·`원`·`통`** 네 자를 더하고, 조각 라벨(`뚜껑`, `바닥`, `앞면`, `윗단`, `아랫단`, `뒷면`)에 필요한 글자도 함께 센다.

`scripts/build-korean-font.py`의 `CHARS`와 `src/core/pdf.ts`의 `KOREAN_FONT_CHARS`를 같이 고치고 스크립트를 돌린다. **목록만 고치고 스크립트를 안 돌리면 조용히 빈칸으로 인쇄된다** — `tests/pdf.test.ts`가 base64를 풀어 글리프가 실제로 들어 있는지 확인하므로 먼저 실패한다.

## 8. 다운로드 기록

### 8.1 종류 구분

지금 시트에는 `가로·높이·바닥폭`뿐이라 원통 기록이 섞이면 구분이 안 된다. **`종류` 열을 `탭` 다음에 넣는다.**

```
시각 | 탭 | 종류 | 가로 | 높이 | 바닥폭 | 용지 | 시접 | 반접기
```

- 사각은 `box`, 원통은 `round`를 보낸다
- 원통도 치수 칸 셋을 그대로 쓴다. **`가로`에 지름, `높이`에 옆면 높이, `바닥폭`에 뚜껑 높이**를 넣는다. 열을 새로 만들면 두 종류가 서로 빈 칸을 만들어 피벗이 지저분해진다. 열 이름이 원통에는 안 맞지만, `종류`를 보면 무슨 값인지 알 수 있다
- 이미 쌓인 줄은 `종류`가 비는데, 시트에서 `box`로 채운다
- 원통에는 반접기가 없으므로 늘 `FALSE`
- **뒷면 비율은 기록하지 않는다.** 기본값에서 벗어나는 일이 드물어 열 하나를 더 만들 값어치가 없다. 나중에 궁금해지면 그때 더한다

### 8.2 분당 상한

주소는 번들에 들어가므로 누구나 꺼낼 수 있다. 저장소를 비공개로 해도 마찬가지다 — 브라우저가 값을 보내야 하니 어차피 공개된다.

작정한 사람은 막을 수 없다. 클라이언트에 토큰을 심어도 번들에 같이 들어가 소용없고, Apps Script의 `doPost`는 요청 헤더를 못 읽어 Origin 검사도 못 한다.

**막을 수 있는 건 멍청한 폭주뿐이고, 그것만 막아도 할당량이 날아가는 사고는 피한다.** `CacheService`로 분당 줄 수를 세고 상한을 넘으면 조용히 버린다. 상한은 60줄로 둔다 — 사람이 1분에 60번 다운로드할 일은 없다.

이상 징후는 짧은 시간에 몰린 줄, 같은 `탭` 값의 반복, 사람이 안 쓸 치수로 알아본다. 실제로 문제가 되면 Cloudflare Worker로 옮긴다. 거기서는 Origin 검사와 IP 기반 제한이 된다. **지금 하는 것은 과하다.**

## 9. 테스트

사각 파우치와 같은 결로 간다. 순수 계산만 시험하고 브라우저 것은 시험하지 않는다.

- **조각 치수** — 골든 케이스 `130/130/30`에서 `Hb = 90`, 조각 넷의 재단 치수
- **둘레 일치** — 모든 유효 입력에서 `Lf + Lb = D × π`
- **범위 검증** — 경계값과 조합 위반(`Hl > Hs/2`, `Hb ≤ 0`)
- **배치** — 조각이 겹치지 않는다, 줄 순서가 늘 같다, 전체 크기가 조각을 모두 담는다
- **종이 장수** — 표 4.2의 값
- **폰트** — 새 글자가 서브셋과 글꼴 바이너리에 실제로 들어 있다 (기존 테스트가 자동으로 잡는다)
- **기록 페이로드** — `종류`가 `round`로 들어간다, 열 순서가 시트와 맞는다

## 10. 미해결 사항
